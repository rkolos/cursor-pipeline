# Команда /task-pipeline [папка-с-задачами]

Универсальный конвейер задач для **любого** проекта. Папка содержит описания задач (`*.md`), имена файлов задают порядок выполнения (`001-…`, `002-…`). Каждая задача проходит цикл:

**план → фактчек плана → реализация → ревью реализации → фикс-план → коммит/пуш → отметка «выполнено»**.

Работает в **Agent mode** (Plan mode не нужен). После закрытия задачи stop-hook **сам** стартует следующую в том же чате (`config.continueNextTask`, по умолчанию `true`). Новый чат / повторный `/task-pipeline` нужны только при `blocked`, исчерпанном контексте или `continueNextTask: false`.

## Состояние

Скрипт: `node ~/.cursor/task-pipeline/tp-state.mjs` (далее `TP`). Запускай из корня воркспейса.

- `TP init <папка>` — создать/досинхронизировать `<папка>/.pipeline/state.json` (новые файлы задач добавляются в конец со статусом `todo`, статусы существующих сохраняются) и сделать папку активной для этого воркспейса.
- `TP next` — что делать дальше: `resume` | `start` | `blocked` | `all-done`.
- `TP show <id|префикс>`, `TP set <id|префикс> --status S --phase P`, `TP summary`.

Статусы: `todo | in-progress | blocked | done`. Фазы: `plan | fact | awaiting-approval | implement | check | fix | commit | done`. Менять статус/фазу **только** через `TP set` — от этого зависит автопродолжение (stop-hook) и пакетный прогон.

Статус отражается в имени файла задачи: `001-foo.md` → `001-foo.in-work.md` (in-progress и blocked) → `001-foo.done.md`. `TP set` переименовывает файл сам и переписывает ссылки на него в `.md`/`.json` папки задач. Поэтому путь к файлу задачи всегда бери из `TP show <id>` (поле `file`), не запоминай его; `id` (имя без суффикса) не меняется. Не переименовывай файлы задач вручную.

Артефакты задачи — `<папка>/.pipeline/runs/<id>/`: `plan.md`, `fact-report.md`, `check-report.md`, `fix-plan.md`, `questions.md`.

Настройки — блок `config` в `state.json` (пользователь может править руками):

- `gateAfterFact` (по умолчанию `false`) — после фактчека остановиться и ждать подтверждения плана;
- `maxCheckRounds` (`2`) — максимум раундов ревью;
- `push` (`true`) — пушить после коммита;
- `reviewModel` (`null`) — модель для субагентов фактчека/ревью; `null` — как у текущего чата;
- `continueNextTask` (`true`) — после `done` stop-hook сразу запускает следующую todo в том же чате; `false` — только уведомление и новый чат с `/task-pipeline`.

Если в запросе есть `TP_AUTONOMOUS=1` (пакетный прогон `~/.cursor/task-pipeline/run-loop.sh`) — `gateAfterFact` игнорируется.

## 0. Старт

1. Если указана папка — `TP init <папка>`. Если не указана — `TP next`; если скрипт сообщает, что активной папки нет, попроси пользователя указать папку и остановись.
2. По `TP next`:
   - `all-done` — сообщи, что все задачи закрыты, остановись;
   - `blocked` — прочитай `questions.md` задачи. Если у вопроса есть **Рекомендация:** и пустой `Ответ:` — запиши рекомендацию в `Ответ:` (не спрашивай пользователя). Если у **всех** вопросов заполнен `Ответ:` (в т.ч. авто из рекомендации) — `TP set <id> --status in-progress` (фаза сохраняется) и продолжай. Иначе покажи незаполненные вопросы без рекомендации и остановись;
   - `start` — `TP set <id> --status in-progress --phase plan`;
   - `resume` — продолжай с текущей фазы; прочитай существующие артефакты, завершённые фазы не переделывай.
3. Одной строкой сообщи пользователю: задача (`position`), фаза, с которой стартуешь.

## 1. Контекст проекта (в начале каждой задачи)

Схема не знает проект заранее — выясни сам и держи в голове на все фазы:

- правила проекта: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`, `CONTRIBUTING.md` — они имеют приоритет над дефолтами этой команды;
- как проверять код: скрипты в `package.json` / `Makefile` / `pyproject.toml` / `Cargo.toml` / CI-конфиг (lint, typecheck, test, build);
- есть ли в проекте своя процедура коммита (команда в `.cursor/commands/` с «commit»/«коммит» в имени, правило или раздел в документации);
- куда проект велит записывать отложенную работу (todo/backlog-файл из правил). Если нигде не сказано — `<папка>/.pipeline/todo.md`;
- в папке задач может быть собственный индекс со статусами (README, `_index.json` и т.п.) — его тоже обновляй при закрытии задачи, сохраняя формат.

## 2. phase = plan

1. Прочитай файл задачи целиком и всё, на что он ссылается (роадмап, спеки, соседние задачи-зависимости).
2. Собери контекст по коду: CodeGraph, если доступен (`codegraph_context` → один `codegraph_explore`), иначе семантический/текстовый поиск. Если задача опирается на результат предыдущих задач — проверь их фактический код, а не описание.
3. Напиши `runs/<id>/plan.md`:
   - **Цель** — один абзац;
   - **Out of scope**;
   - **Шаги** — конкретные файлы/символы (новые и изменяемые);
   - **DoD / приёмка** — наблюдаемые критерии «сделано, когда …»;
   - **Как проверить** — конкретные команды проекта и ручной сценарий при необходимости;
   - **Edge cases** — каждый со ссылкой на пункт DoD.
4. `TP set <id> --phase fact`.

## 3. phase = fact

1. Запусти **субагента** (Task, `subagent_type: generalPurpose`, модель — `reviewModel`, если задана) с промптом:
   > Прочитай `~/.cursor/commands/tp-fact.md` и выполни его. Воркспейс: `<workspace>`. Папка задач: `<tasksDir>`. Задача: `<id>`. Последней строкой верни status.
2. Если субагенты недоступны — выполни `tp-fact.md` сам, **перечитав** план и код заново как независимый ревьюер.
3. Результат:
   - `status: needs-answers` → если у всех вопросов есть `Рекомендация:` или непустой `Ответ:` — заполни пустые `Ответ:` рекомендацией, **не** ставь `blocked`, продолжай как `ok`. Иначе `TP set <id> --status blocked`, покажи вопросы без рекомендации, остановись;
   - `status: ok`, `gateAfterFact: true` и нет `TP_AUTONOMOUS=1` → `TP set <id> --phase awaiting-approval`; покажи краткое резюме плана и вердикт фактчека, спроси «план ок — продолжать?», остановись;
   - иначе → `TP set <id> --phase implement`.

## 4. phase = awaiting-approval

Сообщение пользователя «ок / дальше / /task-pipeline» при этой фазе — подтверждение плана. Если пользователь дал правки — внеси их в `plan.md`. `TP set <id> --phase implement`.

## 5. phase = implement

1. Реализуй `plan.md` по шагам, соблюдая правила проекта.
2. Проверки — связанные с изменениями (lint/typecheck, узкие тесты). Полный прогон не обязателен, если правила проекта не требуют иного.
3. Процессы, запущенные для проверки (серверы, воркеры), останови до конца фазы.
4. Если в этой фазе поднимались тесты/testcontainers/`docker compose` для проверки — сразу выполни **Docker cleanup** (см. § «Docker cleanup»).
5. Отложенную работу вне scope задачи — одной строкой туда, куда велит проект (см. п. 1).
6. Продуктовая развилка, не решённая в плане → вопрос в `questions.md`. Если есть **Рекомендация:** — заполни `Ответ:`, примени её и продолжай (не `blocked`). `blocked` только если рекомендации нет.
7. `TP set <id> --phase check`.

## 6. phase = check

1. Номер раунда `R` = число разделов `## Раунд` в `check-report.md` + 1.
2. Запусти **субагента** (как в фазе fact) с промптом:
   > Прочитай `~/.cursor/commands/tp-check.md` и выполни его. Воркспейс: `<workspace>`. Папка задач: `<tasksDir>`. Задача: `<id>`. Раунд: `<R>`. Последней строкой верни status.
3. Если субагенты недоступны — выполни `tp-check.md` сам, перечитав дифф заново.
4. Результат:
   - `status: clean` → `TP set <id> --phase commit`;
   - `status: needs-answers` → то же правило, что в фазе fact: рекомендация → заполнить `Ответ:` и не блокировать; иначе `blocked`;
   - `status: has-findings` → `TP set <id> --phase fix`.

## 7. phase = fix

1. Реализуй **весь** `fix-plan.md` (блокеры → критичные → минорные), проверяя каждый пункт.
2. Если после фиксов снова гонялись тесты с Docker/testcontainers — выполни **Docker cleanup** (см. § «Docker cleanup»).
3. Если `R < maxCheckRounds` → `TP set <id> --phase check`.
4. Иначе: если после фиксов остались незакрытые блокеры/критичные — вопрос в `questions.md`; с рекомендацией заполни `Ответ:` и иди в `commit`; без рекомендации — `blocked`. Если блокеров нет — `TP set <id> --phase commit`.

## 8. phase = commit

Если в проекте есть своя процедура коммита — выполняй её, дополняя пунктами ниже там, где она молчит. **Исключение:** при `TP_AUTONOMOUS=1` (пакетный `run-loop.sh`) полные проверки из процедуры коммита проекта **не** выполняются — см. п. 2a; остальные шаги коммита/пуша из процедуры проекта сохраняются.

На всей фазе до успешного `git commit` статус задачи — `in-progress`, phase — `commit`. Не считай задачу закрытой, пока commit не прошёл.

1. **Remote:** `git fetch origin`. Если текущая ветка отстаёт от `origin/<branch>` — выведи чужие коммиты (hash, автор, subject) и `git merge origin/<branch>`. Конфликт → `git merge --abort`, опиши в `questions.md`, `TP set <id> --status blocked`, остановись.
2. **Проверки:**
   - **Обычный режим** (нет `TP_AUTONOMOUS=1`): все проектные проверки (lint, typecheck, test, build — что есть / что велит процедура коммита). Падение → исправь и повтори; не выходит → `TP set <id> --phase fix`, опиши в `fix-plan.md`, остановись с отчётом.
   - **`TP_AUTONOMOUS=1` (обязательно, п. 2a):** только **узкие** проверки по изменениям задачи — см. ниже. Полный прогон **запрещён**.
3. **Docker cleanup (обязательно):** перед финальным commit — всегда выполни § «Docker cleanup», даже если в этой задаче Docker «вроде не трогали». Не пропускать.
4. **Резюме в чат** (без ожидания ответа): ветка, число файлов, 2–5 буллетов сути, черновик сообщения.
5. **Один commit с rename задачи:**
   1. Подготовить все изменения задачи (код, docs, индекс папки задач при необходимости).
   2. `TP set <id> --status done --phase done` (rename `.in-work` → `.done`, обновление ссылок).
   3. `git add` только своё: файлы задачи, отложенные задачи (если меняли), папку задач с `.pipeline/` (чтобы попал rename). Без секретов и посторонних незакоммиченных файлов.
   4. `git commit` с сообщением в стиле `git log -10 --oneline` и ссылкой на `<id>`.
6. **Если `git commit` упал** после шага 5.2: немедленно `TP set <id> --status in-progress --phase commit --force` (файл снова `.in-work`), опиши причину в `fix-plan.md`, останься в phase `commit` (или уйди в `fix` по правилам проверок). Задача **не** done.
7. **`git push`**, если `push: true`. Ошибка push **не** откатывает done: запиши в файл отложенных задач и упомяни в итоге. Шаги проекта «после пуша» — так же не блокируют done.

### 2a. Проверки при `TP_AUTONOMOUS=1` (run-loop)

Цель — не гонять полный suite на каждой задаче пакетного прогона.

**Запрещено** (даже если так написано в `/коммит`, `precommit-check` или аналоге проекта):

- `npm run precommit-check` (и любые алиасы «lint+test+typecheck+build» одной командой);
- полный `npm run test` / `npm test` по всему репозиторию;
- полный `npm run lint` по всему репозиторию;
- полный `npm run build` «на всякий случай».

**Обязательный минимум:**

1. Узкие тесты по затронутым модулям/файлам (jest с путями к `*.spec.ts` / каталогам из диффа задачи; e2e — только если задача явно про e2e).
2. `npm run typecheck` (или эквивалент проекта), если скрипт есть.

Падение минимума → исправь в scope задачи и повтори; не выходит → `TP set <id> --phase fix`, опиши в `fix-plan.md`, остановись с отчётом.

В итоге коммита укажи, что прогнан **focused** check (какие пути jest + typecheck), а не full precommit.

## 9. Итог

Коротко: задача закрыта, `git log -1 --format='%h %s'`, что проверено, результат Docker cleanup (reclaimed space / что оставлено), что отложено, какая задача следующая (`TP next`). **Не** начинай следующую задачу в этом же ходе — остановись после итога: при `continueNextTask: true` stop-hook пришлёт followup на следующую todo; при `false` или `all-done` — сообщи пользователю (новый чат `/task-pipeline` только если hook не продолжит).

Итог заканчивай **утверждением**, а не вопросом: «Дальше по конвейеру — `<id>`.» Не спрашивай «Продолжать?», «Переходить к следующей?», «Продолжать в этом чате?» — ответ на это уже есть в `state.json`, а вопрос в последней строке stop-hook трактует как запрос к человеку и может остановить конвейер.

## Docker cleanup

**Обязательный** шаг по окончании работы над задачей (фаза `commit`, п. 3) и сразу после любого прогона тестов с Docker в `implement`/`fix`. Цель — убрать мусорные тестовые контейнеры (testcontainers и т.п.), не трогая живой dev-стек.

Безопасные команды (по порядку):

```bash
docker container prune -f
docker image prune -f
docker builder prune -f
# Только анонимные тома testcontainers (64-hex). Named volumes (postgres_data / redis_data / …) не трогать.
docker volume ls -q | while read -r v; do
  [ -z "$v" ] && continue
  echo "$v" | grep -qE '^[0-9a-f]{64}$' && docker volume rm "$v" 2>/dev/null || true
done
```

Перед prune убедись, что **не** останавливаешь и **не** удаляешь контейнеры в статусе `Up` (compose-имена вроде `*-postgres-*`, `*-redis-*`, dev-стек проекта).

Запрещено без явной просьбы пользователя: `docker system prune -a`, полный `docker volume prune` (он может задеть named volumes dev-БД), `docker stop`/`docker rm` на работающие контейнеры. Удаление **только** anonymous hash-томов (`^[0-9a-f]{64}$`) — разрешено и обязательно (как в `scripts/dev-up.sh`).

Если `docker` недоступен — одной строкой в итоге: cleanup пропущен (нет docker), задачу не блокируй.

В итоге кратко: сколько удалено / `Total reclaimed space`, какие контейнеры оставлены намеренно.

## Правила конвейера

- Продуктовые решения не принимать молча **без записи**: фиксируй в `questions.md` с вариантами. Если указана **Рекомендация:** — сразу пиши её в `Ответ:` и продолжай работу; **`blocked` только если рекомендации нет**.
- Вопросы пользователю (без рекомендации): `questions.md` + `blocked`. Если короткий вопрос уместнее задать прямо в чате — задай его **последней строкой ответа, оканчивающейся на `?`**, и остановись. Не задавай вопрос в середине ответа, продолжая работу.
- Терминалы: команды запускай в блокирующем режиме в текущей сессии; фоновые процессы (серверы, watch) — только если без них нельзя проверить задачу, и останавливай их в той же фазе.
- **Docker cleanup обязателен** по окончании задачи (фаза `commit`) и после тестовых прогонов с Docker — см. § «Docker cleanup». Не закрывай задачу, не выполнив его (кроме случая «docker недоступен»).
- Коммит включает переименование файла задачи (`.in-work.md` → `.done.md`) — стейджи папку задач целиком, чтобы git увидел rename.
- Одновременно `in-progress` — одна задача (скрипт проверяет).
- Не пропускать фазы и не править `state.json` руками в процессе работы.
- Правила проекта и явные инструкции пользователя важнее дефолтов этой команды.
