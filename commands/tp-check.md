# Команда /tp-check

Критический аудит **уже выполненной** реализации задачи по её плану для `/task-pipeline`. Plan mode не нужен: результат — файлы. Обычно вызывается субагентом; вручную: `/tp-check <id>`.

## Вход

- `node ~/.cursor/task-pipeline/tp-state.mjs show <id>` (или с `--dir <tasksDir>`) → `file`, `runDir`, `tasksDir`.
- План: `<runDir>/plan.md`.
- Реализация: незакоммиченные изменения — `git status`, `git diff`, `git diff --staged`, новые untracked-файлы. Папку задач и её `.pipeline/` не аудируй — это служебное.
- Правила проекта: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`.
- Повторный раунд: предыдущие разделы `check-report.md` и `fix-plan.md` — проверь, что прошлые findings действительно закрыты.

## Жёсткие правила

- Код только читаешь. Пишешь только `check-report.md` и `fix-plan.md` (и при необходимости `questions.md`) в `<runDir>`.
- Не чинить findings в этом прогоне.
- Не выдумывать проблемы: при нехватке данных — в открытые вопросы.
- Разрешены read-only проверки: lint, typecheck, узкие тесты по затронутым модулям. Не запускать миграции против общих БД и не поднимать долгоживущие сервисы.
- Структурные вопросы (кто вызывает, что сломается) — через CodeGraph, если доступен.

## Приоритет проверки

1. **Логические конфликты и регрессии:** противоречия в новой логике; конфликт с существующими вызывающими и контрактами; расхождение слоёв (API / БД / UI / фоновые задачи / тесты).
2. **Ошибки реализации:** неверная логика, сломанные ветки и импорты; проглоченные исключения, неверные дефолты; падения на реальных данных.
3. **Edge cases:** null/partial; пустые списки, нулевые лимиты, already-done; неизвестные enum-значения; race/retry/partial success/timeout; права и изоляция данных; обратная совместимость; границы и off-by-one. Для каждого: обработка + тест, либо это finding.
4. **Правила проекта** — нарушения являются findings.
5. **Покрытие плана** (вторично): каждый пункт DoD — `сделано` / `частично` / `не сделано`.

## Выход

### `<runDir>/check-report.md` — дописать раздел `## Раунд <R>`

1. **Вердикт** (2–4 предложения).
2. **Покрытие плана** — пункты DoD со статусами.
3. **Findings** по убыванию серьёзности (Блокеры / Критичные / Минорные), каждый:
   - **Где:** файл / символ / поток
   - **Что не так**
   - **Почему важно**
   - **Критерий «исправлено»**
4. **Открытые вопросы.**

### `<runDir>/fix-plan.md` — только если есть findings (перезаписать)

Упорядоченные задачи на **все** findings (блокеры → критичные → минорные): файлы, что сделать, как проверить. Никаких «рекомендаций на потом». Finding, требующий продуктового решения, — вопрос в `questions.md` (формат как в `tp-fact.md`) вместо задачи. Если в вопросе есть **Рекомендация:** — сразу заполни `Ответ:` этим вариантом и **не** возвращай `needs-answers` (оставь finding в отчёте с пометкой «принято по рекомендации», а закрытие — в `fix-plan.md`). `needs-answers` только если рекомендации нет.

Если findings нет — удали `fix-plan.md`, если он остался от прошлого раунда.

### Последняя строка ответа

`status: clean` | `status: has-findings` | `status: needs-answers`
