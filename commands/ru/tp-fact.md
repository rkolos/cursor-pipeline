# Команда /tp-fact

Фактчек **ещё не реализованного** плана задачи для `/task-pipeline`. Plan mode не нужен: вход и выход — файлы. Обычно вызывается субагентом; вручную: `/tp-fact <id>` (папка задач — активная, см. `node ~/.cursor/task-pipeline/tp-state.mjs show <id>`).

## Вход

- `node ~/.cursor/task-pipeline/tp-state.mjs show <id>` (или с `--dir <tasksDir>`) → `file`, `runDir`.
- План: `<runDir>/plan.md`. Если его нет — верни `status: no-plan`.
- Файл задачи и всё, на что он ссылается.
- Правила проекта: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`, спеки/доки, на которые они указывают.

## Цель (всё сразу)

1. Фактчек плана против реального кода, спек и файла задачи.
2. Логические конфликты внутри плана и с существующим поведением.
3. Незакрытые edge cases.
4. Полнота и проверяемость DoD.
5. **Сразу исправить план** — перезаписать `plan.md` целиком (согласованный текст, не список замечаний).

## Жёсткие правила

- Меняешь только `plan.md`, `fact-report.md` и при необходимости `questions.md` в `<runDir>`. Код, конфиги, тесты, доки проекта не трогать.
- Не расширять scope. Дыру закрывать минимально: шаг, явный out-of-scope или вопрос.
- Не выдумывать API, файлы, флаги, контракты — проверять. Структурные вопросы — через CodeGraph, если доступен.
- Опциональное («можно позже», «nice to have») не выкидывать молча: в шаги/DoD, явный out-of-scope с обоснованием или вопрос.
- Правила проекта — обязательные критерии фактчека.

## 1) Фактчек

- файлы, символы, роуты существуют и делают то, что написано;
- контракты (API, схемы, события) совпадают со спеками проекта;
- «уже есть» / «написать с нуля» — правда;
- план опирается на фактический код предыдущих задач, а не на их описание;
- шаги не меняют то, что план сам запретил трогать.

Ложные факты — исправить в тексте шагов.

## 2) Логические конфликты

Шаг A против шага B; «не трогать X» vs шаг, меняющий X; два источника правды без правила победы; конфликт с существующими вызывающими; взаимоисключающие подходы «на всякий случай»; DoD без шага и шаг без критерия. Выбрать согласованный вариант и переписать, а не пометить «учесть».

## 3) Edge cases

Только применимые: пустые/null/partial данные; ошибки внешних вызовов, retry, partial success, таймауты; гонки и повторная доставка событий; права/tenant isolation; лимиты и off-by-one; обратная совместимость данных и API; идемпотентность миграций. Каждый — шаг + критерий в DoD либо явный out-of-scope.

## 4) Полнота DoD

В итоговом `plan.md`: цель одним абзацем; **Out of scope**; шаги с конкретными файлами; **DoD** — «сделано, когда …»; **Как проверить** — конкретные команды проекта; каждый in-scope edge case отражён в приёмке.

## Продуктовые развилки

Если выбор нельзя вывести из кода, задачи и доков — не решай молча. Допиши в `<runDir>/questions.md`:

```markdown
## Q<n>: <вопрос>
Контекст: …
Варианты: A) … — последствия; B) … — последствия
Рекомендация: A
Ответ:
```

- Если есть **Рекомендация:** (буква/токен варианта) — сразу запиши её в `Ответ:` и **примени в плане**. Это не `needs-answers`: не блокируй задачу.
- `status: needs-answers` — **только** если у вопроса нет рекомендации и пустой `Ответ:` (остальной план всё равно исправь).
- Уже заполненные `Ответ:` — применить в плане, повторно не спрашивать.

## Выход

1. Перезаписанный `plan.md`.
2. `fact-report.md`: **Вердикт** (2–4 предложения); **Что исправлено** — буллеты «факт / конфликт / edge case / DoD»; **Вопросы** — ссылки на Q<n> или «нет».
3. Последняя строка ответа: `status: ok` или `status: needs-answers`.
