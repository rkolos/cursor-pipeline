# Команда /task-pipeline [тека-з-задачами]

Універсальний конвеєр задач для **будь-якого** проєкту. Тека містить описи задач (`*.md`); імена файлів задають порядок виконання (`001-…`, `002-…`). Кожна задача проходить цикл:

**план → фактчек плану → реалізація → рев’ю реалізації → фікс-план → коміт/пуш → позначка «виконано»**.

Працює в **Agent mode** (Plan mode не потрібен). Після закриття задачі stop-hook **сам** стартує наступну в тому ж чаті (`config.continueNextTask`, за замовчуванням `true`). Новий чат / повторний `/task-pipeline` потрібні лише при `blocked`, вичерпаному контексті або `continueNextTask: false`.

## Стан

Скрипт: `node ~/.cursor/task-pipeline/tp-state.mjs` (далі `TP`). Запускай з кореня воркспейсу.

- `TP init <тека>` — створити/досинхронізувати `<тека>/.pipeline/state.json` (нові файли задач додаються в кінець зі статусом `todo`, статуси наявних зберігаються) і зробити теку активною для цього воркспейсу.
- `TP next` — що робити далі: `resume` | `start` | `blocked` | `all-done`.
- `TP show <id|префікс>`, `TP set <id|префікс> --status S --phase P`, `TP summary`.

Статуси: `todo | in-progress | blocked | done`. Фази: `plan | fact | awaiting-approval | implement | check | fix | commit | done`. Змінюй статус/фазу **лише** через `TP set` — від цього залежить автопродовження (stop-hook) і пакетний прогін.

Статус відображається в імені файлу задачі: `001-foo.md` → `001-foo.in-work.md` (in-progress і blocked) → `001-foo.done.md`. `TP set` перейменовує файл і переписує посилання в `.md`/`.json` теки задач. Шлях до файлу задачі завжди бери з `TP show <id>` (поле `file`); `id` (ім’я без суфікса) не змінюється. Не перейменовуй файли задач вручну.

Артефакти задачі — `<тека>/.pipeline/runs/<id>/`: `plan.md`, `fact-report.md`, `check-report.md`, `fix-plan.md`, `questions.md`.

Налаштування — блок `config` у `state.json` (можна правити руками):

- `gateAfterFact` (за замовчуванням `false`) — після фактчеку зупинитися й чекати підтвердження плану;
- `maxCheckRounds` (`2`) — максимум раундів рев’ю;
- `push` (`true`) — пушити після коміту;
- `reviewModel` (`null`) — модель для субагентів фактчеку/рев’ю; `null` — як у поточного чату;
- `continueNextTask` (`true`) — після `done` stop-hook одразу стартує наступну todo в тому ж чаті; `false` — лише повідомлення й новий чат з `/task-pipeline`;
- `lang` (`en` | `uk` | `ru`) — локаль рядків CLI/hook.

Якщо в запиті є `TP_AUTONOMOUS=1` (пакетний прогін `~/.cursor/task-pipeline/run-loop.sh`) — `gateAfterFact` ігнорується.

## 0. Старт

1. Якщо вказано теку — `TP init <тека>`. Якщо ні — `TP next`; якщо скрипт каже, що активної теки немає, попроси користувача вказати теку й зупинись.
2. За `TP next`:
   - `all-done` — повідом, що всі задачі закриті, зупинись;
   - `blocked` — прочитай `questions.md` задачі. Якщо в питанні є **Рекомендація:** і порожня `Відповідь:` — запиши рекомендацію у `Відповідь:` (не питай користувача). Якщо у **всіх** питань заповнена `Відповідь:` (зокрема авто з рекомендації) — `TP set <id> --status in-progress` (фаза зберігається) і продовжуй. Інакше покажи незаповнені питання без рекомендації й зупинись;
   - `start` — `TP set <id> --status in-progress --phase plan`;
   - `resume` — продовжуй з поточної фази; прочитай наявні артефакти, завершені фази не переробляй.
3. Одним рядком повідом користувачу: задача (`position`), фаза, з якої стартуєш.

## 1. Контекст проєкту (на початку кожної задачі)

Схема не знає проєкт наперед — з’ясуй сам і тримай у голові на всі фази:

- правила проєкту: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`, `CONTRIBUTING.md` — вони мають пріоритет над дефолтами цієї команди;
- як перевіряти код: скрипти в `package.json` / `Makefile` / `pyproject.toml` / `Cargo.toml` / CI (lint, typecheck, test, build);
- чи є у проєкті своя процедура коміту (команда в `.cursor/commands/` з «commit»/«коміт» у імені, правило чи розділ у документації);
- куди проєкт велить писати відкладену роботу (todo/backlog з правил). Якщо ніде не сказано — `<тека>/.pipeline/todo.md`;
- у теці задач може бути власний індекс зі статусами (README, `_index.json` тощо) — його теж оновлюй при закритті задачі, зберігаючи формат.

## 2. phase = plan

1. Прочитай файл задачі повністю і все, на що він посилається (роадмап, спеки, сусідні задачі-залежності).
2. Збери контекст по коду: CodeGraph, якщо доступний (`codegraph_context` → один `codegraph_explore`), інакше семантичний/текстовий пошук. Якщо задача спирається на результат попередніх — перевір їх фактичний код, а не опис.
3. Напиши `runs/<id>/plan.md`:
   - **Мета** — один абзац;
   - **Out of scope**;
   - **Кроки** — конкретні файли/символи (нові й змінювані);
   - **DoD / приймання** — спостережувані критерії «зроблено, коли …»;
   - **Як перевірити** — конкретні команди проєкту і ручний сценарій за потреби;
   - **Edge cases** — кожен із посиланням на пункт DoD.
4. `TP set <id> --phase fact`.

## 3. phase = fact

1. Запусти **субагента** (Task, `subagent_type: generalPurpose`, модель — `reviewModel`, якщо задана) з промптом:
   > Прочитай `~/.cursor/commands/tp-fact.md` і виконай його. Воркспейс: `<workspace>`. Тека задач: `<tasksDir>`. Задача: `<id>`. Останнім рядком поверни status.
2. Якщо субагенти недоступні — виконай `tp-fact.md` сам, **перечитавши** план і код знову як незалежний рев’юер.
3. Результат:
   - `status: needs-answers` → якщо в усіх питань є `Рекомендація:` або непорожня `Відповідь:` — заповни порожні `Відповідь:` рекомендацією, **не** став `blocked`, продовжуй як `ok`. Інакше `TP set <id> --status blocked`, покажи питання без рекомендації, зупинись;
   - `status: ok`, `gateAfterFact: true` і немає `TP_AUTONOMOUS=1` → `TP set <id> --phase awaiting-approval`; покажи коротке резюме плану й вердикт фактчеку, спитай «план ок — продовжувати?», зупинись;
   - інакше → `TP set <id> --phase implement`.

## 4. phase = awaiting-approval

Повідомлення користувача «ок / далі / /task-pipeline» на цій фазі — підтвердження плану. Якщо користувач дав правки — внеси їх у `plan.md`. `TP set <id> --phase implement`.

## 5. phase = implement

1. Реалізуй `plan.md` за кроками, дотримуючись правил проєкту.
2. Перевірки — пов’язані зі змінами (lint/typecheck, вузькі тести). Повний прогін не обов’язковий, якщо правила проєкту не вимагають іншого.
3. Процеси, запущені для перевірки (сервери, воркери), зупини до кінця фази.
4. Якщо в цій фазі піднімались тести/testcontainers/`docker compose` — одразу виконай **Docker cleanup** (див. § «Docker cleanup»).
5. Відкладену роботу поза scope задачі — одним рядком туди, куди велить проєкт (див. п. 1).
6. Продуктова розвилка, не вирішена в плані → питання в `questions.md`. Якщо є **Рекомендація:** — заповни `Відповідь:`, застосуй її й продовжуй (не `blocked`). `blocked` лише якщо рекомендації немає.
7. `TP set <id> --phase check`.

## 6. phase = check

1. Номер раунду `R` = кількість розділів `## Раунд` / `## Round` у `check-report.md` + 1.
2. Запусти **субагента** (як у фазі fact) з промптом:
   > Прочитай `~/.cursor/commands/tp-check.md` і виконай його. Воркспейс: `<workspace>`. Тека задач: `<tasksDir>`. Задача: `<id>`. Раунд: `<R>`. Останнім рядком поверни status.
3. Якщо субагенти недоступні — виконай `tp-check.md` сам, перечитавши диф знову.
4. Результат:
   - `status: clean` → `TP set <id> --phase commit`;
   - `status: needs-answers` → те саме правило, що у fact: рекомендація → заповнити `Відповідь:` і не блокувати; інакше `blocked`;
   - `status: has-findings` → `TP set <id> --phase fix`.

## 7. phase = fix

1. Реалізуй **весь** `fix-plan.md` (блокери → критичні → мінорні), перевіряючи кожен пункт.
2. Якщо після фіксів знову ганялись тести з Docker/testcontainers — виконай **Docker cleanup** (див. § «Docker cleanup»).
3. Якщо `R < maxCheckRounds` → `TP set <id> --phase check`.
4. Інакше: якщо після фіксів лишились незакриті блокери/критичні — питання в `questions.md`; з рекомендацією заповни `Відповідь:` і йди в `commit`; без рекомендації — `blocked`. Якщо блокерів немає — `TP set <id> --phase commit`.

## 8. phase = commit

Якщо в проєкті є своя процедура коміту — виконуй її, доповнюючи пунктами нижче там, де вона мовчить. **Виняток:** при `TP_AUTONOMOUS=1` (пакетний `run-loop.sh`) повні перевірки з процедури коміту проєкту **не** виконуються — див. п. 2a; інші кроки коміту/пуша з процедури проєкту зберігаються.

На всій фазі до успішного `git commit` статус задачі — `in-progress`, phase — `commit`. Не вважай задачу закритою, доки commit не пройшов.

1. **Remote:** `git fetch origin`. Якщо поточна гілка відстає від `origin/<branch>` — виведи чужі коміти (hash, автор, subject) і `git merge origin/<branch>`. Конфлікт → `git merge --abort`, опиши в `questions.md`, `TP set <id> --status blocked`, зупинись.
2. **Перевірки:**
   - **Звичайний режим** (немає `TP_AUTONOMOUS=1`): усі проєктні перевірки (lint, typecheck, test, build — що є / що велить процедура коміту). Падіння → виправ і повтори; не виходить → `TP set <id> --phase fix`, опиши в `fix-plan.md`, зупинись зі звітом.
   - **`TP_AUTONOMOUS=1` (обов’язково, п. 2a):** лише **вузькі** перевірки за змінами задачі — див. нижче. Повний прогін **заборонено**.
3. **Docker cleanup (обов’язково):** перед фінальним commit — завжди виконай § «Docker cleanup», навіть якщо в цій задачі Docker «ніби не чіпали». Не пропускати.
4. **Резюме в чат** (без очікування відповіді): гілка, число файлів, 2–5 булетів суті, чернетка повідомлення.
5. **Один commit із rename задачі:**
   1. Підготувати всі зміни задачі (код, docs, індекс теки задач за потреби).
   2. `TP set <id> --status done --phase done` (rename `.in-work` → `.done`, оновлення посилань).
   3. `git add` лише своє: файли задачі, відкладені задачі (якщо змінювали), теку задач із `.pipeline/` (щоб потрапив rename). Без секретів і сторонніх незакомічених файлів.
   4. `git commit` із повідомленням у стилі `git log -10 --oneline` і посиланням на `<id>`.
6. **Якщо `git commit` впав** після кроку 5.2: негайно `TP set <id> --status in-progress --phase commit --force` (файл знову `.in-work`), опиши причину в `fix-plan.md`, лишись у phase `commit` (або йди в `fix` за правилами перевірок). Задача **не** done.
7. **`git push`**, якщо `push: true`. Помилка push **не** відкочує done: запиши у файл відкладених задач і згадай у підсумку. Кроки проєкту «після пуша» так само не блокують done.

### 2a. Перевірки при `TP_AUTONOMOUS=1` (run-loop)

Мета — не ганяти повний suite на кожній задачі пакетного прогону.

**Заборонено** (навіть якщо так написано в `/коміт`, `precommit-check` чи аналозі проєкту):

- `npm run precommit-check` (і будь-які аліаси «lint+test+typecheck+build» однією командою);
- повний `npm run test` / `npm test` по всьому репозиторію;
- повний `npm run lint` по всьому репозиторію;
- повний `npm run build` «про всяк випадок».

**Обов’язковий мінімум:**

1. Вузькі тести за зачепленими модулями/файлами (jest зі шляхами до `*.spec.ts` / каталогів із дифа задачі; e2e — лише якщо задача явно про e2e).
2. `npm run typecheck` (або еквівалент проєкту), якщо скрипт є.

Падіння мінімуму → виправ у scope задачі й повтори; не виходить → `TP set <id> --phase fix`, опиши в `fix-plan.md`, зупинись зі звітом.

У підсумку коміту вкажи, що прогнано **focused** check (які шляхи jest + typecheck), а не full precommit.

## 9. Підсумок

Коротко: задача закрита, `git log -1 --format='%h %s'`, що перевірено, результат Docker cleanup (reclaimed space / що залишено), що відкладено, яка задача наступна (`TP next`). **Не** починай наступну задачу в цьому ж ході — зупинись після підсумку: при `continueNextTask: true` stop-hook надішле followup на наступну todo; при `false` або `all-done` — повідом користувачу (новий чат `/task-pipeline` лише якщо hook не продовжить).

Підсумок закінчуй **твердженням**, а не питанням: «Далі по конвеєру — `<id>`.» Не питай «Продовжувати?», «Переходити до наступної?», «Продовжувати в цьому чаті?» — відповідь уже є в `state.json`, а питання в останньому рядку stop-hook трактує як запит до людини й може зупинити конвеєр.

## Docker cleanup

**Обов’язковий** крок по закінченні роботи над задачею (фаза `commit`, п. 3) і одразу після будь-якого прогону тестів із Docker у `implement`/`fix`. Мета — прибрати сміттєві тестові контейнери (testcontainers тощо), не чіпаючи живий dev-стек.

Безпечні команди (по порядку):

```bash
docker container prune -f
docker image prune -f
docker builder prune -f
# Лише анонімні томи testcontainers (64-hex). Named volumes (postgres_data / redis_data / …) не чіпати.
docker volume ls -q | while read -r v; do
  [ -z "$v" ] && continue
  echo "$v" | grep -qE '^[0-9a-f]{64}$' && docker volume rm "$v" 2>/dev/null || true
done
```

Перед prune переконайся, що **не** зупиняєш і **не** видаляєш контейнери в статусі `Up` (compose-імена на кшталт `*-postgres-*`, `*-redis-*`, dev-стек проєкту).

Заборонено без явного прохання користувача: `docker system prune -a`, повний `docker volume prune` (може зачепити named volumes dev-БД), `docker stop`/`docker rm` на працюючі контейнери. Видалення **лише** anonymous hash-томів (`^[0-9a-f]{64}$`) — дозволено й обов’язково.

Якщо `docker` недоступний — одним рядком у підсумку: cleanup пропущено (немає docker), задачу не блокуй.

У підсумку коротко: скільки видалено / `Total reclaimed space`, які контейнери залишено навмисно.

## Правила конвеєра

- Продуктові рішення не приймати мовчки **без запису**: фіксуй у `questions.md` з варіантами. Якщо вказана **Рекомендація:** — одразу пиши її в `Відповідь:` і продовжуй роботу; **`blocked` лише якщо рекомендації немає**.
- Питання користувачу (без рекомендації): `questions.md` + `blocked`. Якщо коротке питання доречніше поставити прямо в чаті — постав його **останнім рядком відповіді, що закінчується на `?`**, і зупинись. Не став питання всередині відповіді, продовжуючи роботу.
- Термінали: команди запускай у блокувальному режимі в поточній сесії; фонові процеси (сервери, watch) — лише якщо без них не можна перевірити задачу, і зупиняй їх у тій же фазі.
- **Docker cleanup обов’язковий** по закінченні задачі (фаза `commit`) і після тестових прогонів із Docker — див. § «Docker cleanup». Не закривай задачу, не виконавши його (крім випадку «docker недоступний»).
- Коміт включає перейменування файлу задачі (`.in-work.md` → `.done.md`) — стейджи теку задач цілком, щоб git побачив rename.
- Одночасно `in-progress` — одна задача (скрипт перевіряє).
- Не пропускати фази й не правити `state.json` руками в процесі роботи.
- Правила проєкту й явні інструкції користувача важливіші за дефолти цієї команди.
