# Команда /tp-check

Критичний аудит **уже виконаної** реалізації задачі за її планом для `/task-pipeline`. Plan mode не потрібен: результат — файли. Зазвичай викликається субагентом; вручну: `/tp-check <id>`.

## Вхід

- `node ~/.cursor/task-pipeline/tp-state.mjs show <id>` (або з `--dir <tasksDir>`) → `file`, `runDir`, `tasksDir`.
- План: `<runDir>/plan.md`.
- Реалізація: незакомічені зміни — `git status`, `git diff`, `git diff --staged`, нові untracked-файли. Теку задач і її `.pipeline/` не аудитуй — це службове.
- Правила проєкту: `AGENTS.md`, `CLAUDE.md`, `.cursorrules`, `.cursor/rules/`.
- Повторний раунд: попередні розділи `check-report.md` і `fix-plan.md` — перевір, що минулі findings справді закриті.

## Жорсткі правила

- Код лише читаєш. Пишеш лише `check-report.md` і `fix-plan.md` (і за потреби `questions.md`) у `<runDir>`.
- Не лагодити findings у цьому прогоні.
- Не вигадувати проблеми: при нестачі даних — у відкриті питання.
- Дозволені read-only перевірки: lint, typecheck, вузькі тести за зачепленими модулями. Не запускати міграції проти спільних БД і не піднімати довгоживучі сервіси.
- Структурні питання (хто викликає, що зламається) — через CodeGraph, якщо доступний.

## Пріоритет перевірки

1. **Логічні конфлікти й регресії:** суперечності в новій логіці; конфлікт із наявними викликачами й контрактами; розходження шарів (API / БД / UI / фонові задачі / тести).
2. **Помилки реалізації:** хибна логіка, зламані гілки й імпорти; проковтнуті винятки, хибні дефолти; падіння на реальних даних.
3. **Edge cases:** null/partial; порожні списки, нульові ліміти, already-done; невідомі enum-значення; race/retry/partial success/timeout; права й ізоляція даних; зворотна сумісність; межі й off-by-one. Для кожного: обробка + тест, або це finding.
4. **Правила проєкту** — порушення є findings.
5. **Покриття плану** (вторинно): кожен пункт DoD — `зроблено` / `частково` / `не зроблено`.

## Вихід

### `<runDir>/check-report.md` — дописати розділ `## Раунд <R>`

1. **Вердикт** (2–4 речення).
2. **Покриття плану** — пункти DoD зі статусами.
3. **Findings** за спаданням серйозності (Блокери / Критичні / Мінорні), кожен:
   - **Де:** файл / символ / потік
   - **Що не так**
   - **Чому важливо**
   - **Критерій «виправлено»**
4. **Відкриті питання.**

### `<runDir>/fix-plan.md` — лише якщо є findings (перезаписати)

Упорядковані задачі на **усі** findings (блокери → критичні → мінорні): файли, що зробити, як перевірити. Жодних «рекомендацій на потім». Finding, що потребує продуктового рішення, — питання в `questions.md` (формат як у `tp-fact.md`) замість задачі. Якщо в питанні є **Рекомендація:** — одразу заповни `Відповідь:` цим варіантом і **не** повертай `needs-answers` (лиш finding у звіті з позначкою «прийнято за рекомендацією», а закриття — у `fix-plan.md`). `needs-answers` лише якщо рекомендації немає.

Якщо findings немає — видали `fix-plan.md`, якщо він лишився від минулого раунду.

### Останній рядок відповіді

`status: clean` | `status: has-findings` | `status: needs-answers`
